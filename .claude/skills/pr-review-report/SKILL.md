# PR Review Report Generator

GitHub PRの変更内容を分析し、概要・概念図・レビューを含むHTMLレポートを生成する。

## 前提条件

- `gh` CLI がインストールされ、認証済みであること
- レビュー対象のリポジトリへの読み取りアクセスがあること

## 入力形式

ユーザーは以下のいずれかの方法でPRを指定する：

### パターン1: PR URLを直接指定
```
以下のPRをレビューして
https://github.com/org/repo/pull/123
https://github.com/org/sub-repo/pull/456
```

### パターン2: 親リポジトリPRからサブモジュールPRを自動検出
```
このPRをレビューして（サブモジュールも含めて）
https://github.com/org/parent-repo/pull/789
```

どちらのパターンかはユーザーの指示から判断する。パターン2の場合は「サブモジュール自動検出」の手順に従う。

いずれのパターンでも、ユーザーはレビューの参考ドキュメントを追加で指定できる：
```
以下のPRをレビューして
https://github.com/org/repo/pull/123
参考: docs/coding-guidelines.md, docs/architecture.md
```

## 実行フロー

### ステップ1: レビューコンテキストの確認

ユーザーがPR URLと一緒にドキュメントやファイルを指定しているか確認する。
指定されている場合、それらをレビューの判断基準として取り込む。

指定されうるドキュメントの例：
- 設計ドキュメント、ADR（Architecture Decision Record）
- コーディング規約、スタイルガイド
- API仕様書（OpenAPI等）
- プロジェクト固有のレビューチェックリスト
- 既存のアーキテクチャ図や説明資料

ドキュメントの指定方法：
- ローカルファイルパス（例: `docs/architecture.md`）
- リポジトリ内のパス（`gh` で取得可能なもの）
- 会話中に直接貼り付けられたテキスト

指定されたドキュメントが存在する場合は内容を読み込み、レビュー時の追加の評価基準として使用する。
例えばコーディング規約が渡された場合、デフォルトの3観点に加えてその規約への準拠もチェックする。

ドキュメントが指定されていない場合はデフォルトの3観点（設計・コード品質・パフォーマンス）のみでレビューする。

### ステップ2: PR情報の取得

各PRについて以下を取得する：

```bash
# PR メタデータ
gh pr view {PR_URL} --json title,body,author,baseRefName,headRefName,labels,createdAt,updatedAt

# 変更ファイル一覧
gh pr diff {PR_URL} --name-only

# diff 全体
gh pr diff {PR_URL}

# PRコメント・レビューコメント（既存の議論を把握するため）
gh pr view {PR_URL} --json comments,reviews
```

差分が非常に大きい場合（目安: 2000行超）は、ファイル単位で分割して処理すること。
その場合、重要度の高いファイル（ソースコード）を優先し、自動生成ファイルやロックファイルは除外する。

### ステップ3: サブモジュールPR検出（パターン2の場合）

親PRの description（body）からサブモジュールのPR URLを抽出する。

```bash
# PRのbodyを取得
gh pr view {PR_URL} --json body --jq '.body'
```

bodyの中から GitHub PR URL パターン（`https://github.com/{owner}/{repo}/pull/{number}`）をすべて抽出する。
親PR自身のURLは除外し、残ったURLをサブモジュールPRの候補とする。

抽出結果をユーザーに確認する：
「PR descriptionから以下のサブモジュールPR URLを検出しました。これらも含めてレビューしますか？」

PR URLが1つもbodyに含まれていない場合は、サブモジュールPRなしとして親PRのみをレビューする。
ユーザーが追加のPR URLを手動で指定したい場合はそれも受け付ける。

### ステップ4: 変更の分析

取得した全PRのdiffを統合的に分析し、以下を整理する：

#### 4a. 変更概要
- 変更の目的・背景（PRのdescriptionとdiffから推測）
- 影響範囲（変更されたモジュール、レイヤー、機能領域）
- 変更の規模（追加/削除行数、ファイル数）
- リポジトリ間の依存関係と変更の連動性

#### 4b. 概念図の生成（Mermaid記法）

変更内容に応じて適切な図を選択・生成する。以下は選択の指針：

| 変更の性質 | 推奨する図 |
|---|---|
| クラス/インターフェースの追加・変更 | クラス図 |
| API呼び出しフローの変更 | シーケンス図 |
| 状態遷移の追加・変更 | 状態遷移図 |
| モジュール間依存の変更 | コンポーネント図 |
| データフローの変更 | フローチャート |

生成する図には以下の情報を含める：
- **変更前後の差分が分かるようにする**（新規追加は緑系、削除は赤系、変更は黄色系のスタイルで区別）
- 複数リポジトリにまたがる場合は、リポジトリ境界を明示する
- 図は1つに限定しない。変更の全体像を伝えるために必要な数だけ生成する

#### 4c. レビュー

以下の3つの観点からレビューする。各観点で具体的なコード箇所を引用すること。

**1. 設計・アーキテクチャの妥当性**
- 責務の分離は適切か
- 既存アーキテクチャとの一貫性があるか
- 拡張性・保守性への影響
- リポジトリ間のインターフェース設計は適切か（複数リポの場合）

**2. コード品質・可読性**
- 命名の適切さ
- 複雑度（ネストの深さ、関数の長さ）
- エラーハンドリングの適切さ
- テストの充足度

**3. パフォーマンス影響**
- N+1クエリなどのDB関連リスク
- メモリ使用量への影響
- 不要な処理やループ
- キャッシュ戦略への影響

各指摘事項には重要度を付与する：
- 🔴 **Critical**: マージ前に必ず修正すべき
- 🟡 **Warning**: 修正を推奨
- 🔵 **Info**: 提案・改善のアイデア

ユーザーからドキュメント（コーディング規約、設計資料等）が指定されている場合は、上記に加えてそのドキュメントの基準でも評価する。
その場合、レポートにはドキュメント由来の指摘であることを明記する。

### ステップ5: HTML レポートの生成

`assets/report-template.html` をテンプレートとして使用する。
テンプレートの `{{REPORT_DATA}}` プレースホルダーにJSON形式のレビューデータを埋め込む。

レポートに含める構成：
1. **ヘッダー**: レビュー日時、対象PR一覧（URLリンク付き）、レビュアー（Claude）
2. **エグゼクティブサマリー**: 変更の概要を3-5文で。総合評価（Critical/Warning/Infoの件数）
3. **変更概要セクション**: 目的、影響範囲、変更規模の詳細
4. **概念図セクション**: Mermaidで描画した図（複数可）。各図にはタイトルと説明を付与
5. **レビュー詳細セクション**: 観点別の指摘事項。コード引用はシンタックスハイライト付き
6. **リポジトリ別サマリー**: 複数リポの場合、各リポジトリの変更と指摘を個別にまとめる
7. **総合所見**: 全体を通じた推奨事項

### ステップ6: 出力先の確認と保存

HTMLファイルの保存先をユーザーに提案する。提案のルール：

1. カレントディレクトリが対象リポジトリ内なら → `./review-reports/pr-{番号}-{日付}.html`
2. それ以外なら → `~/pr-reviews/pr-{番号}-{日付}.html`

例: 「レビューレポートを `./review-reports/pr-123-20260304.html` に保存しますがよろしいですか？」

ユーザーの確認を得てからファイルを書き出す。

## 出力品質の基準

- HTMLは単一ファイルで完結すること（外部依存なし。CSS/JS/Mermaidすべてインライン or CDN）
- Mermaid.jsはCDNから読み込む: `https://cdn.jsdelivr.net/npm/mermaid/dist/mermaid.min.js`
- シンタックスハイライトはPrism.jsをCDNから使用（ライトテーマ）
- 白背景ベースのシンプル・モダンなデザイン
- レスポンシブデザイン（モバイルでも閲覧可能）
- 印刷用スタイルも含める

## エラーハンドリング

- `gh` CLIが未インストール or 未認証 → エラーメッセージを出し、セットアップ手順を案内
- PR URLが無効 → URLの形式を確認し、正しい形式を案内
- 差分取得失敗（権限不足等） → 原因を特定し、必要な権限を案内
- サブモジュールPRが見つからない → PR descriptionにURLが含まれていない旨を伝え、手動指定を促す
